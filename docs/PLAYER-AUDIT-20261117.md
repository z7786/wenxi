# 播放器性能与稳定性审查（2026-11-17）

> 第一批已在本地实施，见 [实现与验证记录](PLAYER-HARDENING-20261117.md)。下文保留修改前的审查依据；本次落实第 1、2、4 项的第一批措施及第 10 项的监测开关转发；分阶段资源计数、图形兼容、缓存等其余建议不表示已实现。

> 后续已落实缓存压力回收、小窗和 iOS 视口、暂停采样、进度合并、画质恢复与切集计时，见 [后续实现记录](PLAYER-FOLLOWUP-20261117.md)。以下仍为修改前的审查，具体完成范围和真机限制以后续记录为准。

本次审查当前本地代码、前一次异步属性修复，以及 `logs/文析助手-logs-2.3.5-235-1794828620301187.zip`。本报告是分析和实施建议，本轮没有修改播放器行为、编译或发布安装包。

目前建议继续完善 media_kit / libmpv：优先消除异常等待与销毁阻塞，再验证 Android 图形兼容性，随后优化低内存策略、小窗和 iOS 输出尺寸。不能仅凭这些日志认定需要更换整个播放内核。

## 证据范围

- 当前各平台主后端统一由 `lib/playback/playback_backend_factory.dart` 创建 MediaKitBackend。Windows 独立小窗直接创建 Player，有一套单独流程。
- 日志包导出版本是 2.3.5+235，实际 8 次播放加载全部来自 2.3.1+231；不能作为当前未发布修复的验证结果。
- 系统退出历史共 12 条：主进程 ANR 3 次、主进程原生崩溃 1 次，其余包含上滑强杀、更新替换、系统后台清理和其他进程结束。仅一条 ANR 提供了可定位到同步 mpv 属性读取的完整栈。
- 01:05:59 的 SIGABRT 出现在 Android BLASTBufferQueue / Flutter Vulkan 提交链路。缺少 abort message，无法进一步确定根因。
- 85 条播放内存样本中，主进程 PSS 约 309–720 MiB。一个连续播放约 21 分钟的会话从约 336 增至 491 MiB，同时代理缓存由约 8 增至 66 MiB。缓存、解码器、运行时和图形内存都在其中，增长不能直接等同泄漏。
- 214 条 Flutter 时序样本按日志报告的约 120 Hz 预算统计，约 5.7% 的 Flutter 帧超预算，最大 build 约 93 ms。该数据不是视频丢帧率，也不能单凭它归因于播放器控件。
- 8 次 ready 用时约 3.25–6.74 秒，取链占 1.78–3.32 秒；剩余时间包含退出旧会话、探测、初始化、元数据、布局等待等，不等同于解码耗时。日志的首帧由两秒周期采样确认，存在采样延迟，不能作为精确可见首帧计时。

## 1. 优先处理：延迟销毁仍可能阻塞界面

代码：`vendor_plugins/media_kit/lib/src/player/native/player/real.dart:94`、`lib/playback/media_backend.dart:1518`。

`dispose()` 先停止播放、注销事件，然后在五秒后的 Dart 回调中直接调用 `mpv_terminate_destroy`。mpv 0.36 官方头文件明确说明该 API 会阻塞，直到相关客户端和核心退出。延迟执行没有把它移出 UI isolate；解码器或图形驱动结束慢时，仍可能在退出或换集数秒后卡住界面。

目前 `dispose()` 返回时也不表示原生核心已经销毁。快速换集可能短暂保留多个旧核心。不能由此认定日志中的增长就是这些核心泄漏，但生命周期与资源计数需要更准确。

建议把句柄销毁交给专用原生线程或受控工作 isolate，完成前保留回调 trampoline，完成后回收；区分“已停止音画”“已脱离界面”“原生资源已释放”。必须等待在途访问停止，不能简单把五秒改成零，也不能通过强杀正在使用指针的 worker 来回收。

验收：连续换集、关闭后马上重开、Surface 重建期间关闭；同时记录销毁耗时、待销毁实例数和 UI 事件延迟。Windows 普通影片结果不能代替 Android 真机验收。

## 2. 优先处理：异步命令还缺异常收尾

代码：原生 `real.dart:1266`、`:2599`、`:2676`，`media_backend.dart:1082`、`:1533`，`playback_controller.dart:1369`。

前轮读取修复方向正确：请求有编号，事件数据及时复制，读取默认两秒超时，迟到回包忽略。它解决了周期同步读取堵住 UI 的问题，未修改解码质量和缓存。

但属性写入与 command 仍无限等待回包。暂停、切集、渲染尺寸和字幕设置都可能等待这些操作。异常时 UI 可以继续响应，操作队列却不再前进；关闭还会等待同一个属性队列。读属性的两秒超时也不包括初始化之前的等待。

另一个确定的异常路径问题：`_command` 发送立即失败时直接 return，未释放参数指针和请求表项。单次占用不大，属于需要补齐的资源清理，不能据此解释数百 MiB 内存增长。

建议：统一原生请求的 deadline、会话代次、关闭拒绝和迟到回包处理；关键写入失败要传播给调用方。超时代表结果未知，不能把它当写入成功，更不能继续向尚未完成重配的 Surface 写下一步。非关键统计退避重试，关键操作进入受控恢复。

此外，onLoadHooks / onUnloadHooks 由事件分发器 await。若将来在 hook 内 await 依赖同一事件队列的异步 set/get，会出现自等待。当前应用没有注册此类 hook，属于维护边界；不能机械地将 hook 内所有同步调用换成 await 异步调用。

验收：回包被挂起、发送立即失败、初始化不返回、销毁与命令竞争、旧回包晚到；保持 pause/seek/surface 属性顺序。

## 3. 优先验证：Android 图形兼容性是独立问题

代码：`android/app/src/main/AndroidManifest.xml:29`、Android `VideoOutput.java`、`android_video_controller/real.dart`。

应用明确启用 Impeller，历史崩溃栈也确实经过 Flutter Vulkan 提交；mpv 视频输出本身配置的是 Android OpenGL ES。视频解码、mpv 渲染、Flutter 合成是不同环节，切换软件解码不一定能解决合成崩溃。

建议在反馈机型做两个维度的独立对照：保持同一硬解模式对比 Flutter 渲染路径；保持 Flutter 路径对比普通硬解与兼容硬解。采集完整 native abort message、GPU/驱动/Flutter engine 标识、Surface 创建/清理顺序，确认后再限定兼容范围。

Flutter 官方提供 Android 关闭 Impeller 的部署配置，但这是整个 Flutter 引擎的选择，不能当作播放中随意切换的 mpv 参数。必须同时验证现有液态玻璃效果、着色器支持及其他页面。当前没有证据支持全设备关闭 Impeller或默认强制 copy-back。

Surface 清理还值得专项复核：原生 Surface 失效通知通过 Dart 再异步更新 mpv 的 wid/vo，存在必须保证安全的时序窗口；现有日志尚不能证明它就是崩溃触发点。

## 4. 大视频的软件回退策略不统一

代码：`playback_controller.dart:690`、`lib/playback/playback_decoder_recovery.dart`。

播放中解码恢复已经限制软解负载：已知不超过 1080p、帧率等条件满足才尝试。首次打开的硬解失败分支却没有同等分辨率/帧率检查，符合其他条件就重建为软件解码。因此高分辨率片源仍可能在初始化失败后进入高 CPU 路径。

建议统一初始化与播放中恢复策略：区分网络、字幕、渲染、真正解码初始化失败；优先有限次硬解恢复或兼容硬解。已知 4K、高帧率或能力未知时，软解由用户明确选择，并显示实际解码状态。阈值只能是保守策略，1080p 并不保证任何低端 CPU 都能流畅解码。

验收：4K HEVC、10-bit、1080p、高帧率，以及无元数据时初始化失败。验证错误分类、取链不重复、进度和选中音轨保留。

## 5. 缓存已经有上限，但还不识别内存压力

代码：`playback_buffer_policy.dart:25`、`media_backend.dart:1134`、`stream_proxy.dart:1015`。

手机 packet + Range 缓存策略预算 96 MiB，桌面 320 MiB；它们不是整个播放器或整个进程的内存上限。还存在硬解参考帧、显示纹理、libass、Flutter、socket 和对象管理开销。

当前手机缓存策略一致，不区分低内存设备；前向 packet 缓存在一次会话内只增不减；系统内存压力目前有日志和搜索处理，播放器没有对应回收策略。暂停会停止继续预取，但已经分配的缓存保留。

建议低内存档先用 48–64 MiB 作为试验预算，正常设备保持现有策略，根据实际码率、缓冲与压力调整。压力下优先清理远端无读者缓存、取消无关预取；后台较久时渐进收缩。减少 packet 上限后不能马上把同等额度给代理，旧 packet 可能尚未释放。

代价：缓冲减少可能降低弱网抗抖动能力、增加回看时重新请求。高码率媒体应优先保证连续播放，不按文件总大小统一缩小缓存。

## 6. 小窗与 iOS 输出尺寸存在明确优化空间

代码：`independent_player_app.dart:116`、`:131`、`:270`，`floating_playback_host.dart:358`，`media_backend.dart:777`，iOS `VideoOutput.swift:180`。

Windows 独立小窗直接创建 Player，position 等流触发整页 setState，且没有调用主后端的按视口 setSize 策略。应用内悬浮画面也监听整个 controller，未用自身窗口重新设置输出尺寸。小窗不需要持续以大画面尺寸做输出合成。

建议为小窗复用尺寸和状态分流策略：视频纹理稳定挂载，进度控件独立刷新，按窗口物理尺寸（含 DPI）调整输出，拖动时只保留最新目标并延迟应用。多个窗口还需要总缓存/解码实例预算。

iOS 当前被 `_scheduleRenderSize` 平台列表排除，虽然 vendored iOS 插件支持 setSize。未指定输出尺寸时使用视频输出原尺寸，GPU 路径创建三个像素缓冲。4K 在小屏幕显示时仍可能承担较大的输出开销。

建议给 iOS 接入视口尺寸策略，分别验证 iPhone/iPad、横竖屏、字幕、缩放、截图和外接屏。降低输出纹理尺寸通常不降低原始码流的解码分辨率，两类开销应分开衡量。

## 7. 画质降档应更透明、可恢复

代码：`playback_render_policy.dart:49`、`media_backend.dart:1249`、`:798`。

当前连续两次有效窗口丢帧超阈值后，输出宽高各乘 0.75，并调整部分缩放选项；该会话没有自动恢复。像素面积变为约 56%，能降低输出压力，但用户可能感到持续变糊。默认缩放本就使用 bilinear，实际收益主要要看输出面积与触发原因。

建议提供自动平衡/保持画质的明确选择；恢复条件使用更长稳定窗口和冷却期，避免尺寸反复重建。仅在真正持续输出过载时降档，不能把网络缓冲、跳转、后台恢复算作 GPU 跑不动。

旋转保持较大纹理的现有策略也有取舍：减少重建卡顿，但竖屏显存可能较高。建议仅在内存压力或稳定竖屏较久时考虑收缩，避免把旋转卡顿重新带回来。

## 8. 暂停与后台仍有不必要的采样和存储

代码：`media_backend.dart:1075`、`:1104`，`playback_controller.dart:665`、`:1322`，`playback_store.dart:176`，`state_store.dart:349`。

性能采样每两秒启动一次，基础 native 指标每十秒读取。`setVideoMonitoringEnabled(false)` 控制监测资格，不会停止整个采样过程；暂停或后台仍做部分读取、缓存维护与通知。内存统计已在原生工作线程执行，且慢采样自动降到两分钟，这部分应保留。

书签每十秒保存一次，暂停且位置不变也更新 updatedAt 并走全局状态写入。JSON 编码已经放到 compute，但仍要复制状态、持久化并通知 StateStore 监听者。独立小窗五秒心跳也会保存进度。

建议播放稳定时降低非必要统计频率，暂停/后台停掉画面采样，保留确有需要的投屏/PiP监测。书签按实际变化去重，保存尚未完成时合并最新进度；暂停、跳转、切集、退出等关键时刻立即保存。心跳存活检查与进度落盘分开。

若仅把周期从十秒延长，异常退出可能丢失更多进度；优先去掉无变化和重叠写入。不要为节省少量日志而删除错误与生命周期证据。

## 9. 切集路径还可以缩短，但应先保证资源顺序

代码：`playback_controller.dart:523`、`:538`、`:823`、`:1380`。

已有优化：旧音频先暂停，初始化与取链并行，片尾三十秒开始预取下一集链接。当前仍等旧 session 的退休（包含字幕队列、后端关闭、来源清理与保存完成），之后才开始当前新片取链；每次都新建 Player。

建议先增加 retire/resolve/probe/open/presentation/首个可见帧的分段计时。安全条件满足时提前做下一片地址解析，并把不影响来源有效性的持久化移出切集关键路径。来源需要同账号转存、清理临时文件时必须保持原有租约与串行约束。

同格式片源复用 Player/VideoController 有潜在收益，但属于后续高风险优化，需要重置 Headers、缓存、音轨、字幕、播放位置和失败状态。先修复销毁与队列，比先缓存多个解码器稳妥。

## 10. 补齐监测一致性，避免后续误诊

代码：`delegating_backend.dart`、`playback_video_monitor.dart`、`playback_diagnostics.dart:105`、`media_backend.dart:1299`。

- DelegatingPlaybackBackend 缺少 `setVideoMonitoringEnabled` 转发，继承的是空实现。BT 与边下边播包装可能没有正确把后台/投屏状态传给真实后端。补齐后可避免不必要监测或误判。
- 当前画面监测确认的是 mpv 有帧和时间轴推进，无法证明 Flutter/显示合成最终呈现正常。不能因为这项监测通过，就排除图形层冻结或花屏。
- 关闭后八秒的内存采样仍是整个进程值，期间可能已打开另一部视频。需标记活动/退休解码实例数与当前会话，避免把新视频缓存算成旧实例未释放。
- 暂无 iOS/macOS/Windows 同等内存采样，不能把 Android 数据直接外推到所有平台。
- UI超预算、解码丢帧、输出丢帧、网络缓冲、原生命令延迟应分开记录。首帧监测的采样确认时间也应与真实呈现时间区分。

## 已经合理的部分

- 网络代理在独立 isolate 中，常规视频数据不往返 UI isolate；缓存和在途分片有联合上限。
- 实际连接数从 8 开始自适应，并受缓存与来源上限约束。设置 128 不等于持续开 128 个连接；继续提高线程不能解决 GPU/解码/销毁问题。
- 主播放页进度通知限制到约 250 ms；进度和缓冲不会触发全页重建，隐藏控制条不继续订阅进度刷新，视频有 RepaintBoundary。
- 双指动作每显示帧只应用最新变换，手势中不写配置，也不逐帧改变底层输出尺寸。
- 横竖屏尽量复用同一纹理；恢复网络保留播放位置；解码恢复有次数约束；已有 seek 合并。
- 字幕样式与字体有缓存和去重。32 ms 的字幕布局 timer 是一次合并，不是永久每秒执行三十多次原生命令。

## 实施顺序与验收

第一批：异常命令清理和超时策略、真正异步销毁、首次软解回退保护、包装后端监测转发。

第二批：反馈 Android 机型渲染对照、低内存缓存策略、小窗状态分流/尺寸限制、iOS 视口输出。图形兼容改动需单独实验，不和内存改动一次混用。

第三批：采样/书签去重、画质档位恢复、切集关键路径缩短；最后评估后端复用与 libmpv 升级。

Android 当前使用固定校验的 v1.1.7 原生构建，前轮符号核对为 mpv 0.36.0。升级原生库值得做独立分支对照，但不能仅改 pubspec 版本就认为已升级底层，也不能未经验证覆盖现有自定义补丁。

真机验收至少包括：低内存 Android 与反馈 HONOR 机型、普通 1080p、4K HEVC、HDR/10-bit、内嵌 ASS 和外部字幕；持续播放超过用户常见故障时长（建议两小时）、多次换集、横竖屏、后台恢复、断网续播。桌面增加多独立小窗，iOS增加 iPhone/iPad。分别比较首帧/切集/退出耗时、CPU、温度、PSS/图形内存、待回收实例、缓冲及丢帧。

本轮依据为静态代码审查与既有日志统计，没有新的真机性能对照结果，不给出未经测量的提速百分比。前轮真实 Windows libmpv 测试与策略测试通过，只能证明其覆盖范围内的行为。
