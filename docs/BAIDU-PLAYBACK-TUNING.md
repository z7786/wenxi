# 百度大视频播放调整（2026-11-01）

百度默认使用 4 个连接、4 MiB 分片。已保存的网盘连接数和分片设置继续生效。实际连接数以用户设置为上限，从最多 4 个起步；已知时长和文件大小时，以平均码率乘播放速度估计播放所需带宽，接收速度不足其 1.5 倍且缓存较少时再增加连接。429、503 和读取失败仍触发退避。文件缺少大小或时长时保留原来的增长策略。

本次卡顿与 Range 调度有关。部分 MP4 将音频和视频放在相距很远的文件区域，解复用会反复切换两边的读取。字节距离不再作为取消所有旧请求的依据，应用主动拖动进度时仍通过 `prepareSeek()` 取消旧工作。HTTP 响应在发送头后交由底层 socket 处理，监听对端断开，及时清理失效读取，并在取消时中断等待中的发送。

播放器关闭一个读取后，允许已开始且被使用的分片在原缓存预算内完成；后续媒体读取可以加入覆盖它的在途分片。检测到两处较远区域反复交替时，将每个读取的预读窗口收紧为当前和下一个分片，保留已开始的相邻分片，避免每个音频包都取消整片预读。小范围文件头/尾探测仍优先且只复用已经可用的字节。下载缓存播放、文件身份校验、失败重试、暂停和缓存预算继续受原规则约束。

使用一个已存在的百度分享做只读实测：1,851,503,218 字节，HEVC 1080p/30 fps，时长 1,458.956 秒，平均码率约 10.15 Mbit/s。通过项目分享解析和在线播放取链路线取得地址，并用项目实际 Range 代理及 Windows libmpv 解码。视频输出和音频输出设为 null，排除渲染差异；不代表 Android 真机或 GPU 渲染性能。

原实现 4/8 连接拖动到 20 分钟处均超过 40 秒还在缓冲。修复后 4 连接、4 MiB 测试约 3.2 秒起播，拖动约 10.1 秒恢复，随后 50 秒连续播放推进约 51 秒；再拖回 10 分钟处约 13.1 秒恢复，暂停和继续正常。全过程上游尝试 65 次，完成 54 个分片，无分片失败。较早的短测试中 4 连接约 11 秒恢复，上游尝试 32 次。

这些结果针对本机网络和该样本，更多连接没有带来优势。高码率、其他 CDN、账号风控或设备解码能力可能产生不同结果；Android 和 Windows 共用本次调度修复，Android 尚未真机验证。

回归覆盖并发远距离读取、跨轨道分片复用、对端断开时释放未收到数据的请求、明确拖动取消、暂停、缓存上限、凭证与文件身份校验。当前 mpv 参数说明参考 [官方 stream-buffer-size 与缓存文档](https://github.com/mpv-player/mpv/blob/master/DOCS/man/options.rst)，本次未增加解码线程或总缓存上限。
